## Repository layout

- `wireframe/site/` — the original static HTML/JS wireframe (`index.html`, `mobile.html`, `book.html`, `support.js`). It is the design and behavior reference; don't edit it as part of app work.
- `thad-the-barber-ui/` — the Angular 22 app built from the wireframe. All commands below run from this folder.
- `thad-the-barber-express/` — the Express 5 web server (JavaScript, CommonJS) that App Service runs for the site; the zip deploy is this folder with the Angular build in `public/app/thad-the-barber-ui` (one folder per app, so a later portal can sit beside it; `npm run build:express:<env>` in the UI writes it there, plus `csp-sources.json`, `brand.css` and `shop.json` (name, phone and Square booking URL for the error page, BR-14) from its post-build hook, `scripts/write-express-files.ts`). `routes/index.js` serves prerendered pages, the app shell for `clientRoutes` (`/book` until #58) and the prerendered `/404` page with a 404 for anything else; `lib/` holds the per-request CSP nonce, security headers (helmet, `NOINDEX`) and telemetry (Azure Monitor, started from `bin/www` only when `APPLICATIONINSIGHTS_CONNECTION_STRING` is set); `routes/health.js` serves `/healthz`. Thrown errors render the themed `views/error.ejs` (`lib/error-handler.js` middleware, ported from `wireframe/site/error.html`: status, request ID = trace ID, shop phone and Square booking link from `shop.json`, own strict CSP, styled by `public/stylesheets/error.css` over `/brand.css`); the stack trace shows only when `NODE_ENV=development`, which App Service never sets. `ERROR_TEST_ROUTE=true` adds `/_test/error?status=` for tests (Playwright's CI server). Tests: `npm test` (Vitest + supertest against a fake build).
- `thad-the-barber-api/` — the ASP.NET Core (.NET 10) minimal API, `/api/*` only; xUnit v3 tests in the sibling `thad-the-barber-api.tests/`. Run with `dotnet run --project thad-the-barber-api` and test with `dotnet test --solution thad-the-barber-api/thad-the-barber-api.sln` from the repo root (`global.json` pins the SDK and opts into Microsoft.Testing.Platform). Every test run writes Cobertura coverage to `thad-the-barber-api.tests/TestResults/coverage.cobertura.xml` (options in the test csproj's `TestingPlatformCommandLineArguments`; `coverage.config` leaves out generated code). Test folders mirror the API's (one test file per class under test); shared helpers live in `TestSupport/`. Tests host the API through `TestSupport/ApiFactory`, which swaps in `TestSupport/Fakes/FakeSquareService` for the whole Square service, cache included (cache behavior is tested in `SquareCacheTests` and, over fake HTTP, `SquareServiceTests`); pass `new ApiFactory(square: …)` to change what Square returns. Its clients send a valid session token (signed by the in-memory `FakeSessionSigningKey`, minted with `TestSupport/SessionTokens`) and its `FakeRecaptchaService` passes everyone; `CreateClientWithoutToken()` calls as a stranger and `new ApiFactory(recaptcha: …)` changes Google's verdict. Key Vault loads when `KeyVault:Name` is set (only in `appsettings.Development.json`/`appsettings.Test.json`, picked by `ASPNETCORE_ENVIRONMENT`; one `Development` environment covers local runs and the Azure dev app, debug behavior included, so local runs need `az login`; tests run as `Testing` with no vault; prod's `appsettings.Production.json` so far only raises `Recaptcha:MinScore` to 0.7; it will also need `KeyVault:Name` and the Square settings). CORS origins come from `Cors:AllowedOrigins` in Key Vault (dev's list includes `http://localhost:4200`) and startup fails if the list is empty or has a wildcard. Minimal APIs in feature + layer folders, like the Angular app (the user's choice, 2026-09-30, layers added 2026-10-04): every feature folder splits into layer subfolders, and namespaces follow folders. Layer names: `Endpoints/` (`Map…Endpoints` extension methods), `Services/` (interfaces and implementations), `Models/` (records, enums; one type per file; record declarations and `new` calls list one property or argument per line with the closing `)` on its own line), `Mappers/` (`To…` extension methods), `Configuration/` (`*Settings`, `*Setup` with the feature's `Add…` service registration, settings validators, secret names), `Handlers/`, `Checks/` (health checks), `Exceptions/`, `Middleware/`, `Transformers/` (OpenAPI document and operation transformers), `Processors/` (OpenTelemetry processors), `Extensions/` (extension methods). `Features/<Feature>/` holds the API's features (`Features/Health/`, `Features/Booking/` (availability, bookings, and the manage link from #29: `ManageTokenSigner` HMACs the booking ID with the `ManageLink--HmacKey` secret, checked at startup; endpoints read the token from the `X-Manage-Token` header only, and tests sign with `TestSupport/ManageTokens`; `BookingService` refuses a phone whose Square customers would exceed `Booking:MaxUpcomingPerPhone` bookings in any `Booking:CapWindow` stretch with 409 `booking_limit`, BR-13, #35; request bodies reject unknown JSON fields and are capped at 128 KB in every environment), `Features/Shop/`, `Features/Session/`: `POST /api/session` checks the `Origin` against `Cors:AllowedOrigins` and the reCAPTCHA token, then issues a 15-minute ES256 JWT signed in Key Vault by the `session-jwt-signing` key; `Infrastructure/Auth/Configuration/AuthSetup` adds JWT bearer auth, reading the public key at startup, and `Program` requires the token on the whole `/api` group, so every endpoint needs it unless it's marked `AllowAnonymous`, which only `/api/session`, `/api/health`, `/api/shop` (public facts every page loads, so page views spend no reCAPTCHA assessments; #39) and `/api/webhooks/square` are, as `AuthSetupTests` checks); `Recaptcha/` holds Google's reCAPTCHA call (`IRecaptchaService`, which turns every failure into `RecaptchaUnavailableException`, so the bot check fails closed; API key from `Recaptcha--ApiKey`, project in `appsettings.json`, site key in `appsettings.{Environment}.json`), the way `Square/` does for Square; `Square/` holds every Square call (`Services/ISquareService`/`SquareService`; its location, booking profile and catalog reads go through `SquareCache`, which keeps them 60 minutes and serves the last copy, with a logged warning, when Square fails), the webhook (`Endpoints/SquareWebhookEndpoints`, `POST /api/webhooks/square`, bodies capped at 32 K characters (413): `Services/SquareWebhookService` checks the signature with the SDK's `WebhooksHelper` against `Square:WebhookNotificationUrl` and the `Square--WebhookSignatureKey` secret, skips an event id it has handled in the last 24 hours, and marks the shop (`location.updated`) or service (`catalog.version.updated`) entry stale with `SquareCache.MarkStale<T>`, so the next read refetches; booking events aren't subscribed; tests sign with `TestSupport/SquareWebhooks`), the OAuth token renewal and `SquareSettings`. The Square SDK's types are Square's models; they never leave `Square/`. `Square/Mappers` turns them into Square-free models holding only what we use, internal ids included (`Square/Models`: `ShopDetails`, `BookingProfile`, `BookableService`, `TimeSlot`, `Appointment`), and each feature's `Mappers/` turns those into the DTOs (`ShopInfo`, `BookingConfirmation`). The DTOs are the API contract, designed for accuracy, stability and simplicity rather than to fit the wireframe-built UI, which adapts to them (the user's choice, 2026-10-04). They carry data, not presentation: phone in E.164, a structured address, opening hours as `{ day: 0–6, opens: "HH:mm:ss", closes }`, and times as UTC instants (`startAt`; availability is a plain list of them), with `ShopInfo.timeZone` telling the UI to show every time in the shop's timezone, not the browser's. Booleans read as `Is…`/`Can…`/`Has…`. `Common/` holds code any feature can use, in the same layer folders (`Common/Extensions/TimeZoneInfoExtensions`: `zone.ToLocalDate(instant)`, `zone.GetDayRange(date)` and `zone.GetMonthRange(date)` → `Common/Models/DateTimeRange`, DST-safe; `range.Intersect(other)` in `Common/Extensions/DateTimeRangeExtensions`; the folder isn't `Shared/` because that's a VB keyword and CA1716 fails the build). Outcomes the caller can act on (a taken time, details to correct) are exceptions deriving from `Common/Exceptions/ProblemException` (status, `code`, title); `Infrastructure/Problems/Handlers/ProblemExceptionHandler` writes them as ProblemDetails carrying `code` (e.g. 409 `slot_unavailable`), while `Square/Handlers/SquareExceptionHandler` only maps Square and Key Vault failures to 502 `square_rejected`/503 `square_unavailable`. The Square SDK's `SquareApiException` puts Square's whole response body in its message, and Square's error details can repeat a customer's name or phone, so `SquareService` runs every call through `CallSquareAsync`, which throws `Square/Exceptions/SquareRequestFailedException` instead (status plus Square's error category, code and field, never `detail`; the full response is in Square's Developer Console API Logs); `Infrastructure/Problems/Configuration/ProblemsSetup` gives every other error body a `code` (`validation_failed` for validation problems, then by status: `unauthorized`, `not_found`, `rate_limited`…, any other 4xx `bad_request`, 5xx `internal_error`) and `type` `about:blank` where ASP.NET has no RFC link, so every error has `type`, `title`, `status` and `code` (`TestSupport/ProblemAssert` checks all four). Mapper tests read the recorded responses in `Fixtures/Square` with `SquareFixture.ReadAs<T>`; `Infrastructure/<Concern>/` holds app-wide setup (`Auth/`, `Cors/`, `KeyVault/`, `Headers/`, `Problems/`, `RateLimiting/`: fixed-window limits per client IP from `RateLimits:*` on `POST /api/session`, `POST /api/bookings` (BR-13) and cancel/reschedule (their own `Manage` limit, so used-up booking attempts never block managing a booking), 429 with `Retry-After`; `Telemetry/`: OpenTelemetry (in Azure it's the only log provider, so the console never writes unredacted text to the log stream), with `RedactingLogProcessor`/`RedactingSpanProcessor` added ahead of Azure Monitor's exporters so phones and emails are masked, and name/phone/email fields lose their value, before anything is exported (BR-23); `TelemetrySetupTests` books with a made-up customer through `TestSupport/TelemetryCapture` and checks none of it is exported). Configuration classes are named `*Settings` (`*Options` would clash with ASP.NET's `CorsOptions`). One project, no Domain/Infrastructure project split until a second deployable or the database needs it. Keep business rules in plain classes (no `HttpContext` or Square types) and Square behind an interface.

## Architecture

- **Standalone, zoneless, signals.** Files use Angular 22 CLI naming (`home.ts` / class `Home`, no `.component` suffix). Bootstrap is `src/app/app.config.ts`, which `app.config.browser.ts` (adds browser telemetry, `core/telemetry/`) and `app.config.server.ts` (prerender) each merge.
- **Features own their state.** `app.routes.ts` loads `features/home` eagerly (it's the prerendered landing page, so a click shouldn't wait on a second download) and lazy-loads `features/booking`; each `<feature>.routes.ts` registers its effects with `provideEffects`. The root `layout` slice (mobile menu, `src/app/store/`), `shop` (`features/shop/state/`), `announcements` (`features/announcements/state/`), `home` and `booking` are registered at bootstrap, as root reducers in `app.config.ts`: the header and footer read the first four on every page, and shop and booking save only part of their slice, which needs the slice's initial state in place before the saved copy merges over it (a lazy `provideState` slice would lose its unsaved fields). Every derived selector lives on its feature's `extraSelectors`, wrapped one argument per line, with any logic in a named `to…` function and projector parameters named after the field they get. Slices are independent: `AppState` types only `layout`, and nothing reads another slice through it.
- **State folder pattern** (per feature `state/`): `*.state.ts` (interface + initial state), `*.actions.ts` (an `<Slice>ActionTypes` enum of type strings with `[Source]` prefixes such as `[Shop]`/`[Shop API]`, so slices never share a type, plus one `createAction` per action named like `ShopInfoRequest`/`ShopInfoRequestSuccess`/`ShopInfoRequestFailure`, always wrapped one argument per line (even with no props), payloads inline as `props<{ shopInfo: ShopInfo; }>()`; no `createActionGroup`), `*.feature.ts` (`createFeature` + reducer + `extraSelectors`/derived `MemoizedSelector`s), `*.effects.ts` (functional effects calling the feature's services). Put reusable helpers in `shared/utils`.
- **Persistence.** `store/meta/meta.reducers.ts` uses `ngrx-store-localstorage` to sync the `home` slice's SMS signup and the `shop` slice's `shopInfo` (not their load statuses, so every visit refreshes them) to localStorage under `ttb-<key>`, base64-encoded, rehydrating at bootstrap. `booking` saves only `savedConfirmation` (the last booking's ID, time and manage token, never name or phone), and its `deserialize` (`toKeptConfirmation`) keeps it on load only while it's under 24 hours old and the appointment hasn't started (`isKept`, BR-22, #64), and reads nothing else stored under the key. A root effect (`booking-tabs.effects.ts`) copies a booking saved in another tab, so a tab holding none doesn't overwrite it. Its availability must be fresh. `restoreDates: false` keeps saved ISO strings as strings. `home` clears its saved copy with its `State Reset` action. Add a slice to `syncKeys` to persist it.
- **Mocked backend.** `HomeContentService` and `SmsSignupService` return local data (`features/home/data`). Each notes the endpoint it should eventually call. Booking is real (#41): `AvailabilityService` gets `GET /api/bookings/availability?from=&to=` (shop-calendar days, both included, at most 31; only the open days, which the date step lists in full, so a picked day needs no second request; #205) and `BookingService` posts `POST /api/bookings`; the booking page maps the API's ProblemDetails `code` (`shared/models/problem-code.model.ts`) to a `BookingNotice` (`utils/booking-notice.utils.ts`: severity, text, retry; every problem notice ends with call, text and Square's booking site, BR-14), which `NoticeMessage`, the feature's only message component (a booking made is a `Success` notice with a title), shows inline, and a 409 `slot_unavailable` reloads the days in view; the load effect maps its own failure the same way. The slice holds the view (`visibleMonth`: a month, or `null` for the next `UPCOMING_DAY_COUNT` days from today on the shop's clock, `core/config/booking-dates.ts`; the effect turns it into the day range with `toDayRange`, and the date step's month picker and arrows switch it), its open days, their `loadStatus` (the date step shows a spinner while it's pending; the availability notice is derived from it) and `savedConfirmation`, the last booking kept for 24 hours or until it starts, which the page shows at the top, next to the availability notice, after a reload while it's still kept (read once when the page opens); the page keeps the booking form (`models/booking-form.model.ts`: name, phone, date as a shop-calendar ISO day, `startAt`; a `<form [formGroup]>` whose `(ngSubmit)`, from the summary's `type="submit"` button, calls the page's `confirm()`; each step gets the controls it edits as inputs (`[dateControl]`, `[startAtControl]`, …) and binds `[formControl]`, and the page turns the form's value into one `bookingFormValue` signal it passes to the time step and summary, so no child reaches the form through DI; a day's times come from the slice's days), and the page keeps the submit (the form is disabled while it's sent), the retry key, the confirmation and the booking notice, all thrown away with the page; `BookingSummary` shows them from inputs and emits `retry`. The booking window comes from `shopFeature.selectBookingSettings`, and every booking date and time shows on the shop's clock. The mocked e2e fixture serves made-up availability (`e2e/support/booking.ts`); `environments/` has one file per build configuration (`development` local, `devCloud`, `test`, `production`), typed by `environment.model.ts`; build request URLs as `${environment.apiBaseUrl}/path`.
- **Shop data** (name, phone, address, hours, socials, booking settings) comes from Square through `GET /api/shop`, which needs no session token (#39): the root `shop` slice (`features/shop/state/`) loads it in the browser on the first navigation and retries on the next one after a failure, and its `shopFeature` selectors derive the phone links, location and map URLs, hours in minutes and social links. `core/config/shop-info.ts` keeps `SHOP_FALLBACK` (the `ShopInfo` name, E.164 phone and Square booking URL, same field names as the API, shown until the shop loads and on Express's error page), `SHOP_CONTENT` (site content Square doesn't hold: just reviews until #37; it moves into the home slices once they own it) and `HOME_SECTIONS`. There's no venue line or area text ("Route 1 in Fredericksburg"): Square doesn't hold them, and the site shouldn't need upkeep; a later issue may source the venue from Square. `features/shop/services/shop-hours.service.ts` builds the hours table (shown by `features/shop/components/hours-list`) and the live "Open now" status from the slice, on the shop's clock (`timeZone`), not the browser's. Shop models are one type per file in `features/shop/models/`; the generic ones the shared utils use (`weekday`, `week-time`, `phone-links`, `nav-item`) are in `shared/models/`, and `SHOP_FALLBACK`'s and `SHOP_CONTENT`'s in `core/models/`. A feature without a page (shop) still lives in `features/<name>/` with its own `state/`, `services/`, `models/` and `components/`; `store/` keeps only the `layout` slice, `AppState` and the meta reducers. Tests use the made-up `src/testing/test-shop.ts`, which the mocked e2e suite also serves for `/api/shop`.
- **Backdrop.** `shared/components/backdrop` renders the fixed background. `scroll` mode is the wireframe's scroll-scrubbed video: `FrameScrubber` (`frame-scrubber.ts`) progressively loads 7 clips × 121 AVIF frames from `public/assets/frames3/c1..c7` onto a canvas, with keyframes anchored to page sections. `still` mode shows one keyframe (booking page). (The README's "not in this version yet" note about the backdrop predates the scrubber.)

## Theming

Rule: **if PrimeNG has a component for it, restyle it with tokens instead of building a custom component.**

- `src/app/theme/`: `tokens/primitive.ts` (palette, radii, font) → `tokens/semantic.ts` (plus brand values under `semantic.extend.brand`, emitted as `--p-brand-*`) → `tokens/components/*.ts` (one file per PrimeNG component) → `thad-preset.ts` (`definePreset(Aura, …)`).
- `theme/tailwind/theme.css` maps tokens to Tailwind colors/radii and defines named utilities (`glass`, `tile`, `eyebrow`, `section-title`, …).
- `styles.css` sets the CSS layer order `theme, base, primeng, components, utilities` so Tailwind beats PrimeNG without `!important`. Dark scheme is on via `<html class="app-dark">`.
- Tailwind 4 + `tailwindcss-primeui`. **Never PrimeFlex.** PrimeNG 22 needs the license key in `core/config/primeui-license.ts`.

## Conventions (enforced or expected)

Components:
- Templates over 4 lines go in a `.html` file.
- A page section or other single-use component selects its own state from the store; the page only lays out sections. Inputs are for reusable components (`shared/components`).
- Style a wrapper element in the template, never the host (no `host: { class }`, no `:host`).
- At most 2 plain Tailwind utilities per element; move the rest to a named class in the component `.scss`. Theme utilities and breakpoint prefixes (`md:`, `lg:`) don't count and stay inline.
- SCSS nests to follow the DOM. PrimeNG overlay content (drawer, Galleria lightbox) stays top-level.
- Component SCSS is unlayered and beats Tailwind, so never set in SCSS a property that an inline breakpoint class changes — keep the base value inline too (`px-6 md:px-8`).
- For `nav-link`, set `--link-color`, not `color`.

TypeScript (`eslint.config.js`, plus `eslint/items-per-line.js`):
- Explicit types on every variable, property, parameter (including callbacks/destructuring) and return value. The only exceptions are the `createAction`/`createFeature` declarations, which carry a one-line `eslint-disable` with a reason.
- Semicolons everywhere, including interface/type members.
- One item per line from 3 items (array items, object props, type members, call args, params, destructured props); 1-2 items may stay on one line or be wrapped, with matching brackets. `pipe(...)` wraps from 2 operators. Imports are the exception: they stay on one line and wrap, one name per line, only past 120 characters, as Prettier does.
- ESLint formats `.ts`; Prettier formats HTML/SCSS/CSS only (Prettier would undo the one-per-line wrapping).
- NgRx typing: effects are `FunctionalEffect`; derived selectors are `MemoizedSelector<object, T>`; feature selectors are destructured with `: typeof xFeature`; action payloads are inline `props<{ … }>()` types in every slice; consumers import actions as a namespace (`import * as ShopActions from './shop.actions'`); store is injected as `inject<Store<AppState>>(Store)`.
- `tsconfig.json` is strict with `noUncheckedIndexedAccess`, `noUnused*`, and `strictTemplates`.
- `@microsoft/applicationinsights-*` imports are allowed only in `src/app/core/telemetry/` (`no-restricted-imports`), so switching telemetry providers rewrites that folder only. The browser stays on the App Insights SDK, not OpenTelemetry, which Microsoft doesn't support in browsers.

## Tests

The existing specs encode the wireframe's placeholder behavior (booking rules, hours, mock data), not confirmed business rules. When business rules change, a failing spec may need updating rather than indicating a bug. Keep the existing specs; add new ones per feature (see `docs/wireframe-audit.md` §9).
