# ASP.NET Core API

Moved from CLAUDE.md; read it when working in `thad-the-barber-api/` or on anything the UI sends to `/api/*`.

`thad-the-barber-api/` — the ASP.NET Core (.NET 10) minimal API, `/api/*` only; xUnit v3 tests in the sibling `thad-the-barber-api.tests/`. Run with `dotnet run --project thad-the-barber-api` and test with `dotnet test --solution thad-the-barber-api/thad-the-barber-api.sln` from the repo root (`global.json` pins the SDK and opts into Microsoft.Testing.Platform). Every test run writes Cobertura coverage to `thad-the-barber-api.tests/TestResults/coverage.cobertura.xml` (options in the test csproj's `TestingPlatformCommandLineArguments`; `coverage.config` leaves out generated code). Test folders mirror the API's (one test file per class under test); shared helpers live in `TestSupport/`. Tests host the API through `TestSupport/ApiFactory`, which swaps in `TestSupport/Fakes/FakeSquareService` for the whole Square service, cache included (cache behavior is tested in `StaleCacheTests` and, over fake HTTP, `SquareServiceTests`); pass `new ApiFactory(square: …)` to change what Square returns. Its clients send a valid session token (signed by the in-memory `FakeSessionSigningKey`, minted with `TestSupport/SessionTokens`) and its `FakeRecaptchaService` passes everyone; `CreateClientWithoutToken()` calls as a stranger and `new ApiFactory(recaptcha: …)` changes Google's verdict. Key Vault loads when `KeyVault:Name` is set (only in `appsettings.Development.json`/`appsettings.Test.json`, picked by `ASPNETCORE_ENVIRONMENT`; one `Development` environment covers local runs and the Azure dev app, debug behavior included, so local runs need `az login`; tests run as `Testing` with no vault; prod's `appsettings.Production.json` so far only raises `Recaptcha:MinScore` to 0.7; it will also need `KeyVault:Name` and the Square settings). CORS origins come from `Cors:AllowedOrigins` in Key Vault (dev's list includes `http://localhost:4200`) and startup fails if the list is empty or has a wildcard. Minimal APIs in feature + layer folders, like the Angular app (the user's choice, 2026-09-30, layers added 2026-10-04): every feature folder splits into layer subfolders, and namespaces follow folders. Layer names: `Endpoints/` (`Map…Endpoints` extension methods), `Services/` (interfaces and implementations), `Models/` (records, enums; one type per file; record declarations and `new` calls list one property or argument per line with the closing `)` on its own line), `Mappers/` (`To…` extension methods), `Configuration/` (`*Settings`, `*Setup` with the feature's `Add…` service registration, settings validators, secret names), `Handlers/`, `Checks/` (health checks), `Exceptions/`, `Middleware/`, `Transformers/` (OpenAPI document and operation transformers), `Processors/` (OpenTelemetry processors), `Extensions/` (extension methods). `Features/<Feature>/` holds the API's features (`Features/Health/`, `Features/Booking/` (availability, bookings, and the manage link from #29: `ManageTokenSigner` HMACs the booking ID with the `ManageLink--HmacKey` secret, checked at startup; endpoints read the token from the `X-Manage-Token` header only, and tests sign with `TestSupport/ManageTokens`; `BookingService` refuses a phone whose Square customers would exceed `Booking:MaxUpcomingPerPhone` bookings in any `Booking:CapWindow` stretch with 409 `booking_limit`, BR-13, #35; request bodies reject unknown JSON fields and are capped at 128 KB in every environment), `Features/Shop/`, `Features/Session/`: `POST /api/session` checks the `Origin` against `Cors:AllowedOrigins` and the reCAPTCHA token, then issues a 15-minute ES256 JWT signed in Key Vault by the `session-jwt-signing` key; `Infrastructure/Auth/Configuration/AuthSetup` adds JWT bearer auth, reading the public key at startup, and `Program` requires the token on the whole `/api` group, so every endpoint needs it unless it's marked `AllowAnonymous`, which only `/api/session`, `/api/health`, `/api/shop` (public facts every page loads, so page views spend no reCAPTCHA assessments; #39), `/api/bookings/next?count=` (the home page's next open times as UTC instants, one Square search shared by all visitors for `Booking:NextTimesCacheFor` (30 s) in `NextTimesService`; #221) and `/api/webhooks/square` are, as `AuthSetupTests` checks); `Recaptcha/` holds Google's reCAPTCHA call (`IRecaptchaService`, which turns every failure into `RecaptchaUnavailableException`, so the bot check fails closed; API key from `Recaptcha--ApiKey`, project in `appsettings.json`, site key in `appsettings.{Environment}.json`), the way `Square/` does for Square; `Square/` holds every Square call (`Services/ISquareService`/`SquareService`; its location, booking profile and catalog reads go through `StaleCache`, which keeps them 60 minutes and serves the last copy, with a logged warning, when Square fails), the webhook (`Endpoints/SquareWebhookEndpoints`, `POST /api/webhooks/square`, bodies capped at 32 K characters (413): `Services/SquareWebhookService` checks the signature with the SDK's `WebhooksHelper` against `Square:WebhookNotificationUrl` and the `Square--WebhookSignatureKey` secret, skips an event id it has handled in the last 24 hours, and marks the shop (`location.updated`) or service (`catalog.version.updated`) entry stale with `StaleCache.MarkStale<T>`, so the next read refetches; booking events aren't subscribed; tests sign with `TestSupport/SquareWebhooks`), the OAuth token renewal and `SquareSettings`. The Square SDK's types are Square's models; they never leave `Square/`. `Square/Mappers` turns them into Square-free models holding only what we use, internal ids included (`Square/Models`: `ShopDetails`, `BookingProfile`, `BookableService`, `TimeSlot`, `Appointment`), and each feature's `Mappers/` turns those into the DTOs (`ShopInfo`, `BookingConfirmation`). The DTOs are the API contract, designed for accuracy, stability and simplicity rather than to fit the wireframe-built UI, which adapts to them (the user's choice, 2026-10-04). They carry data, not presentation: phone in E.164, a structured address, opening hours as `{ day: 0–6, opens: "HH:mm:ss", closes }`, and times as UTC instants (`startAt`; availability is a plain list of them), with `ShopInfo.timeZone` telling the UI to show every time in the shop's timezone, not the browser's. Booleans read as `Is…`/`Can…`/`Has…`. `Common/` holds code any feature can use, in the same layer folders (`Common/Extensions/TimeZoneInfoExtensions`: `zone.ToLocalDate(instant)`, `zone.GetDayRange(date)` and `zone.GetMonthRange(date)` → `Common/Models/DateTimeRange`, DST-safe; `range.Intersect(other)` in `Common/Extensions/DateTimeRangeExtensions`; the folder isn't `Shared/` because that's a VB keyword and CA1716 fails the build). Outcomes the caller can act on (a taken time, details to correct) are exceptions deriving from `Common/Exceptions/ProblemException` (status, `code`, title); `Infrastructure/Problems/Handlers/ProblemExceptionHandler` writes them as ProblemDetails carrying `code` (e.g. 409 `slot_unavailable`), while `Square/Handlers/SquareExceptionHandler` only maps Square and Key Vault failures to 502 `square_rejected`/503 `square_unavailable`. The Square SDK's `SquareApiException` puts Square's whole response body in its message, and Square's error details can repeat a customer's name or phone, so `SquareService` runs every call through `CallSquareAsync`, which throws `Square/Exceptions/SquareRequestFailedException` instead (status plus Square's error category, code and field, never `detail`; the full response is in Square's Developer Console API Logs); `Infrastructure/Problems/Configuration/ProblemsSetup` gives every other error body a `code` (`validation_failed` for validation problems, then by status: `unauthorized`, `not_found`, `rate_limited`…, any other 4xx `bad_request`, 5xx `internal_error`) and `type` `about:blank` where ASP.NET has no RFC link, so every error has `type`, `title`, `status` and `code` (`TestSupport/ProblemAssert` checks all four). Mapper tests read the recorded responses in `Fixtures/Square` with `SquareFixture.ReadAs<T>`; `Infrastructure/<Concern>/` holds app-wide setup (`Auth/`, `Cors/`, `KeyVault/`, `Headers/`, `Problems/`, `RateLimiting/`: fixed-window limits per client IP from `RateLimits:*` on `POST /api/session`, `POST /api/bookings` (BR-13) and cancel/reschedule (their own `Manage` limit, so used-up booking attempts never block managing a booking), and the anonymous `GET /api/bookings/next` (`NextTimes`), 429 with `Retry-After`; `Telemetry/`: OpenTelemetry (in Azure it's the only log provider, so the console never writes unredacted text to the log stream), with `RedactingLogProcessor`/`RedactingSpanProcessor` added ahead of Azure Monitor's exporters so phones and emails are masked, and name/phone/email fields lose their value, before anything is exported (BR-23); `TelemetrySetupTests` books with a made-up customer through `TestSupport/TelemetryCapture` and checks none of it is exported). Configuration classes are named `*Settings` (`*Options` would clash with ASP.NET's `CorsOptions`). One project, no Domain/Infrastructure project split until a second deployable or the database needs it. Keep business rules in plain classes (no `HttpContext` or Square types) and Square behind an interface.

**Reviews (#245).** `Features/Reviews`: anonymous `GET /api/reviews` returns `{ testimonials: [{ id, quote, author, source, rating }], rating: { score, count, url } | null }`. `ReviewsService` (singleton) reads the owner's `reviews.json` from the private content container through `IMediaStorage` and keeps it in `StaleCache` until the media webhook marks it stale (or 60 minutes pass). A missing file serves no reviews; an unreadable one keeps the last good copy, or serves no reviews (logged, 200) when there is none yet. `ReviewsFileMapper` is lenient: it skips bad testimonials, defaults `rating` to 5 and `source` to "Customer review", and drops an invalid rating or a non-https link. Google's reviews API replaces the file as the source in #37 behind `ReviewsService`. Tests use `FakeReviewsHttp` and `ApiFactory(reviews:)`.

**Gallery, announcements and media webhook (#204).** The API reads the environment's storage account with its managed identity (`Infrastructure/Storage`: `IMediaStorage`, `AzureMediaStorage` over `Azure.Storage.Blobs`; `MediaStorage:AccountName`, `MediaContainerName` and `ContentContainerName` in `appsettings.{Environment}.json`, short names with the URIs built in code). Anonymous `GET /api/gallery` (`Features/Gallery`) lists the media container's `gallery/` folder (BR-34: jpg/jpeg/png/webp/avif, newest upload first by the blob's creation time, alt text from the file name) as `[{ src, alt, uploadedAt }]`. Anonymous `GET /api/announcements` (`Features/Announcements`) reads `announcements.json` from the private content container, skips invalid items (BR-33; a button link must be a site path, https, tel: or mailto:, with no control characters) and cleans each `bodyHtml` with HtmlSanitizer (`AnnouncementBodySanitizer`), and returns only the ones showing today on the shop's calendar from Square's timezone (BR-30), so a scheduled post never reaches the browser. Both keep their data in `StaleCache` (60 minutes; the last copy is served with a warning when storage fails) and answer 200 with none when storage can't be read and no copy exists, which is cached for a minute so an outage doesn't make every request wait out the timeout. `POST /api/webhooks/media` (`Features/Media`) takes Event Grid's batches: it answers the subscription handshake by echoing `validationCode` (without the key), and `BlobCreated`/`BlobDeleted` in `gallery/` or on `announcements.json` mark that cache stale. Every other call needs the `x-media-webhook-key` header, compared in fixed time with `MediaWebhook:Key` (Key Vault secret `MediaWebhook--Key`); with no key set every call is 401. Tests use `FakeMediaStorage` and `ApiFactory(media:)`.

**Announcements admin (wishlist: admin shell).** `GET /api/admin/announcements` and `PUT /api/admin/announcements` (`Features/Announcements`, `Admin` policy, no-store) edit the same `announcements.json` in the content container. The list returns every item whatever its dates, each with `status` (`showing`, `scheduled`, `ended`, from the shop's calendar like BR-30) and its image as `{ fileName, altText, position, src }`; the save takes `{ items: [...] }` in the file's own shape (`title`, `bodyHtml`, `startDate`, `endDate`, `image: { fileName, altText, position }`, `buttons: [{ label, url, variant }]`), replaces the whole file (an empty list clears it) and marks the public cache stale, so visitors see it at once. A save is checked strictly (the records `AnnouncementInput`, `AnnouncementImageInput`, `AnnouncementButtonInput` carry the rules: title up to 120, at most 50 items and 4 buttons, last day not before the first, a button link allowed by `AnnouncementsFileMapper.IsAllowedLink`, an image named without a folder and with alt text), answering 400 `validation_failed` with `errors`; `bodyHtml` is cleaned with `AnnouncementBodySanitizer` before it is stored. Unlike the public list, a file that can't be read or isn't valid JSON, or a save that fails, is 503 `announcements_unavailable`, so a save never wipes what an outage hid. `IMediaStorage.WriteTextAsync` replaces a blob; the API's identity already has Storage Blob Data Contributor on the content container, so this needs no role change (image upload to the media container, which is read-only today, comes with the gallery admin). Tests: `AdminAnnouncementsServiceTests`, `AdminAnnouncementsEndpointsTests`.

**Shop info admin (wishlist: editable shop info).** The notice on the booking page (`ShopInfo.Notice`, BR-42) is the Square location's description unless the owner set their own. `shop-info.json` in the content container (`{ "notice": "...", "isNoticeShown": true }`, `ShopContentService`, cached like reviews and marked stale by a save and by the media webhook) holds the owner's text and a switch: `GET /api/shop` returns the saved text when there is one, Square's description otherwise, and null when the switch is off. A missing file or one that can't be read yet keeps Square's description, so an outage never costs the page its notice. `GET /api/admin/shop` and `PUT /api/admin/shop` (`AdminShopService`, `Admin` policy, no-store) read and save it: the read returns `{ notice, isNoticeShown, squareNotice }` (`notice` null while Square's text is used, `squareNotice` is what shows then) and the save takes `{ notice, isNoticeShown }` (notice up to 1000 characters, blank saves as none, `isNoticeShown` required), replaces the file and answers with the read. Unlike the public read, an unreadable or invalid file, or a failed save, is 503 `shop_info_unavailable`, so a save never overwrites what an outage hid. More shop fields can join the same file. Tests: `ShopContentServiceTests`, `AdminShopEndpointsTests`, `ShopDtoMapperTests`, `MediaWebhookServiceTests`.

**Gallery admin (wishlist: admin shell).** `GET /api/admin/gallery`, `POST /api/admin/gallery` and `DELETE /api/admin/gallery/{fileName}` (`Features/Gallery`, `AdminGalleryService`, `Admin` policy, no-store) manage the media container's `gallery/` folder. The list is `[{ fileName, src, altText, uploadedAt }]`, newest first (a folder that can't be read is 503 `gallery_unavailable`, not an empty list). An upload is a multipart form with `file` and `altText`: a photo's alt text comes from its file name (BR-34), so the file is stored as the alt text's words, lower case and hyphenated, with the real extension (`GalleryFileNameMapper`: "Skin fade, beard!" becomes `skin-fade-beard.jpg` and reads back as "Skin fade beard"; a name already taken gets `-2`, `-3`…; the alt text is up to 100 characters). The type comes from the file's first bytes (`ImageFileInspector`: JPEG, PNG, WebP or AVIF, never the name or the browser's content type) and a file is at most 25 MB; anything else, a missing file or a missing description is 400 `invalid_image`, and the content type stored is the real one. A delete of a name that is not there, or not a plain stored name, is 404 `photo_not_found`. Every change marks the public gallery stale so visitors see it at once. `POST /api/admin/announcements/images` stores an image for an announcement the same way, in `announcements/` under its own file name's words plus a short random suffix, and answers `{ fileName, src }` to put in the announcement's `image`. The API's identity needs Storage Blob Data Contributor on the media container (`apiMediaWriter` in `environment.bicep`; apply it before uploads work in an environment). Form posts skip antiforgery because the admin token is a bearer header. `IMediaStorage` gained `WriteNewBytesAsync` and `DeleteAsync`. Tests: `AdminGalleryServiceTests`, `AdminGalleryEndpointsTests`, `GalleryFileNameMapperTests`, `ImageFileInspectorTests`, and the image upload tests in the announcements ones.

**Find my bookings (#214, BR-20).** `POST /api/bookings/lookup/code` `{ phone }` (texts the one-time code) always answers 202 with no body, whether or not the phone has bookings (it never asks Square), and `POST /api/bookings/lookup/verified-list` `{ phone, code }` (checks the code) answers `{ bookings: [{ id, startAt, manageToken }], lookupToken, expiresAt }` (upcoming, not cancelled, soonest first, every Square customer with the phone, read up to the booking window's end; nothing is stored) or 400 `code_invalid`. `GET /api/bookings/lookup/verified-list` with the `X-Lookup-Token` header (header only, never the query string; allowed by CORS) answers the current bookings list again without a text code, through the same private `BookingService` method; a missing, malformed, tampered or expired token is 403 `lookup_expired`, not 401, because the UI's session interceptor renews the reCAPTCHA session and retries on every 401. `LookupTokenSigner` signs `base64url(phone|expiry).base64url(mac)` with HMAC-SHA256 under a key derived from `ManageLink--HmacKey` plus a purpose (so a lookup token never validates as a manage token or the reverse), compares in constant time and uses `TimeProvider`; the lifetime is fixed from the check (`Booking:LookupSessionLifetime`, 15 minutes, between 1 minute and 1 hour, overridable in `appsettings.{Environment}.json`), never extended. Headers aren't exported to telemetry, so the token never reaches it (`TelemetrySetupTests` checks). Both live in `BookingEndpoints`/`BookingService` behind the session token. `Twilio/` mirrors `Square/`: `ITwilioVerifyService` (`StartAsync`, `CheckAsync`) over the official `Twilio` package with an API key; a 404 or 429 from the check is a wrong code, any other failure becomes `TwilioRequestFailedException` (status and Twilio error code only) and the handler answers 503 `verification_unavailable`. `TwilioSettings` (`VerifyServiceSid` in `appsettings.Development.json` only so far; secrets `Twilio--AccountSid`, `Twilio--ApiKeySid` and `Twilio--ApiKeySecret` in Key Vault, set with `Set-TtbSecrets.ps1`) is validated at startup only once any value is set, so environments without Twilio still start and answer 503. Limits: per IP `RateLimits:LookupCode` and `LookupVerifiedList` (10 each); the per-phone limits are Twilio's own (five texts in ten minutes, five checks per code), and a sixth text, Twilio's 60203, becomes a `RateLimitedException` (429 `rate_limited`, `Retry-After` 10 minutes). The cloud dev API will not start until `Twilio--AccountSid`, `Twilio--ApiKeySid` and `Twilio--ApiKeySecret` are all in its Key Vault (run `Set-TtbSecrets.ps1` before deploying), because its `appsettings.Development.json` sets the SIDs and the validator then requires the rest. A check counts as a wrong code only for Twilio error 20404 (verification expired, approved or deleted) or 60202 (max check attempts); Twilio gives a wrong Verify service SID the same 20404, so a mistyped SID looks like wrong codes, not a 503. A cancelled caller stops before Twilio is called and is not a failure; an HttpClient timeout is. Tests fake Twilio with `FakeTwilioVerifyService` (`ApiFactory(twilio:)`) and, over HTTP, `FakeTwilioHttp`.

**Photo uploads.** Kestrel's body limit is 128 KB for the whole API (webhooks); the two upload endpoints (`UploadAdminGalleryPhoto`, `UploadAdminAnnouncementImage`) are marked `.AllowImageUpload()` and `UseImageUploadSizeLimit` (`Infrastructure/Storage/Middleware`) raises the limit to the 25 MB photo plus 1 MB of form for them alone; without it any photo over 128 KB got a 413. **Admin sign-in (#95).** `Features/Admin`: `POST /api/admin/session` `{ idToken }` (behind the visitor session token and the session rate limit) takes the Google ID token from Google Identity Services and answers `{ token, expiresAt, email, name }` (`name` is what Google shows for the account, null when it gives none; it is also the token's `name` claim and in `GET /api/admin/me`), a 4-hour (`Admin:Lifetime`) ES256 admin JWT signed by the same Key Vault key as the session token (audience `ttb-admin`, claim `role` = `admin`; `AdminTokenIssuer`). `GoogleIdTokenValidator` checks Google's signature (`GoogleSigningKeys`, from its discovery document, behind `IGoogleSigningKeys` so tests use their own), the issuer, `aud` = `Admin:GoogleClientId`, expiry (by the injected clock) and a verified email; `AdminService` then requires the email in `Admin:AllowedEmails` (case-insensitive) and logs every sign-in and denial with the email masked. Failures: 401 `invalid_id_token`, 403 `not_authorized`, 503 `admin_unavailable`. `AuthSetup` makes the one bearer check accept both audiences, so an admin token also opens the rest of the API; the `Admin` policy (`role` = `admin`) guards every `/api/admin/*` endpoint except the sign-in itself, and `GET /api/admin/me` (`{ email }`) is the first one. `GET /api/admin/config` (visitor session only, since the sign-in page asks before anyone is signed in) answers `{ googleClientId }`, so the UI never holds the client ID itself, or 503 `admin_unavailable` while sign-in isn't set up. The settings are optional on purpose: without `Admin--GoogleClientId` and `Admin--AllowedEmails--N` in Key Vault the API still starts and sign-in answers 503, so a missing secret never takes the public site down. Tests make Google ID tokens with `TestSupport/GoogleIdTokens` and `FakeGoogleSigningKeys` (`ApiFactory.GoogleKeys`), and admin tokens with `TestSupport/AdminTokens`; the test host is configured with `AdminHarness.GoogleClientId` and `AllowedEmail`.

**Contact (#286).** `POST /api/contact` (`Features/Contact`, behind the session token, its own per-IP limit `RateLimits:Contact`, 5 per hour) takes `{ category: "question" | "issue" | "feedback", message, name?, email?, phone?, pageOrBooking? }` and answers 201 `{ id }`. `ContactRequest` holds the rules: `message` always (at most 2000 characters); a `question` or `issue` also needs `name` and an `email` or `phone`; an `issue` also needs `pageOrBooking` (its `message` says what happened); feedback may be anonymous, but any email (valid address) or phone (`+1` and 10 digits) given is still checked. Failures are the usual ProblemDetails: 400 `validation_failed` with `errors` keyed by the PascalCase member name (`Name`, `Email`, `Phone`, `PageOrBooking`, `Message`), 429 `rate_limited`, 401, and 503 `contact_unavailable` when storage can't be written. `ContactService` saves one JSON file per message, `contact/<yyyyMMddTHHmmssZ>-<id>.json`, in the private content container (`IMediaStorage.WriteNewTextAsync` refuses to replace a file; the API's identity has Storage Blob Data Contributor on that container). A `question` or `issue` also logs `ContactNeedsReply` with the category and file name only, which `infra/modules/contact-alerts.bicep` watches (every 15 minutes, one alert per file, to the stage's shared action group); the contact details are only in the file, never in logs or telemetry (`TelemetrySetupTests` checks).
