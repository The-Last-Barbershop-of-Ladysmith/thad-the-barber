# ASP.NET Core API

Moved from CLAUDE.md; read it when working in `thad-the-barber-api/` or on anything the UI sends to `/api/*`.

`thad-the-barber-api/` — the ASP.NET Core (.NET 10) minimal API, `/api/*` only; xUnit v3 tests in the sibling `thad-the-barber-api.tests/`. Run with `dotnet run --project thad-the-barber-api` and test with `dotnet test --solution thad-the-barber-api/thad-the-barber-api.sln` from the repo root (`global.json` pins the SDK and opts into Microsoft.Testing.Platform). Every test run writes Cobertura coverage to `thad-the-barber-api.tests/TestResults/coverage.cobertura.xml` (options in the test csproj's `TestingPlatformCommandLineArguments`; `coverage.config` leaves out generated code). Test folders mirror the API's (one test file per class under test); shared helpers live in `TestSupport/`. Tests host the API through `TestSupport/ApiFactory`, which swaps in `TestSupport/Fakes/FakeSquareService` for the whole Square service, cache included (cache behavior is tested in `StaleCacheTests` and, over fake HTTP, `SquareServiceTests`); pass `new ApiFactory(square: …)` to change what Square returns. Its clients send a valid session token (signed by the in-memory `FakeSessionSigningKey`, minted with `TestSupport/SessionTokens`) and its `FakeRecaptchaService` passes everyone; `CreateClientWithoutToken()` calls as a stranger and `new ApiFactory(recaptcha: …)` changes Google's verdict. Key Vault loads when `KeyVault:Name` is set (only in `appsettings.Development.json`/`appsettings.Test.json`, picked by `ASPNETCORE_ENVIRONMENT`; one `Development` environment covers local runs and the Azure dev app, debug behavior included, so local runs need `az login`; tests run as `Testing` with no vault; prod's `appsettings.Production.json` so far only raises `Recaptcha:MinScore` to 0.7; it will also need `KeyVault:Name` and the Square settings). CORS origins come from `Cors:AllowedOrigins` in Key Vault (dev's list includes `http://localhost:4200`) and startup fails if the list is empty or has a wildcard. Minimal APIs in feature + layer folders, like the Angular app (the user's choice, 2026-09-30, layers added 2026-10-04): every feature folder splits into layer subfolders, and namespaces follow folders. Layer names: `Endpoints/` (`Map…Endpoints` extension methods), `Services/` (interfaces and implementations), `Models/` (records, enums; one type per file; record declarations and `new` calls list one property or argument per line with the closing `)` on its own line), `Mappers/` (`To…` extension methods), `Configuration/` (`*Settings`, `*Setup` with the feature's `Add…` service registration, settings validators, secret names), `Handlers/`, `Checks/` (health checks), `Exceptions/`, `Middleware/`, `Transformers/` (OpenAPI document and operation transformers), `Processors/` (OpenTelemetry processors), `Extensions/` (extension methods). `Features/<Feature>/` holds the API's features (`Features/Health/`, `Features/Booking/` (availability, bookings, and the manage link from #29: `ManageTokenSigner` HMACs the booking ID with the `ManageLink--HmacKey` secret, checked at startup; endpoints read the token from the `X-Manage-Token` header only, and tests sign with `TestSupport/ManageTokens`; `BookingService` refuses a phone whose Square customers would exceed `Booking:MaxUpcomingPerPhone` bookings in any `Booking:CapWindow` stretch with 409 `booking_limit`, BR-13, #35; request bodies reject unknown JSON fields and are capped at 128 KB in every environment), `Features/Shop/`, `Features/Session/`: `POST /api/session` checks the `Origin` against `Cors:AllowedOrigins` and the reCAPTCHA token, then issues a 15-minute ES256 JWT signed in Key Vault by the `session-jwt-signing` key; `Infrastructure/Auth/Configuration/AuthSetup` adds JWT bearer auth, reading the public key at startup, and `Program` requires the token on the whole `/api` group, so every endpoint needs it unless it's marked `AllowAnonymous`, which only `/api/session`, `/api/health`, `/api/shop` (public facts every page loads, so page views spend no reCAPTCHA assessments; #39), `/api/bookings/next?count=` (the home page's next open times as UTC instants, one Square search shared by all visitors for `Booking:NextTimesCacheFor` (30 s) in `NextTimesService`; #221) and `/api/webhooks/square` are, as `AuthSetupTests` checks); `Recaptcha/` holds Google's reCAPTCHA call (`IRecaptchaService`, which turns every failure into `RecaptchaUnavailableException`, so the bot check fails closed; API key from `Recaptcha--ApiKey`, project in `appsettings.json`, site key in `appsettings.{Environment}.json`), the way `Square/` does for Square; `Square/` holds every Square call (`Services/ISquareService`/`SquareService`; its location, booking profile and catalog reads go through `StaleCache`, which keeps them 60 minutes and serves the last copy, with a logged warning, when Square fails), the webhook (`Endpoints/SquareWebhookEndpoints`, `POST /api/webhooks/square`, bodies capped at 32 K characters (413): `Services/SquareWebhookService` checks the signature with the SDK's `WebhooksHelper` against `Square:WebhookNotificationUrl` and the `Square--WebhookSignatureKey` secret, skips an event id it has handled in the last 24 hours, and marks the shop (`location.updated`) or service (`catalog.version.updated`) entry stale with `StaleCache.MarkStale<T>`, so the next read refetches; booking events aren't subscribed; tests sign with `TestSupport/SquareWebhooks`), the OAuth token renewal and `SquareSettings`. The Square SDK's types are Square's models; they never leave `Square/`. `Square/Mappers` turns them into Square-free models holding only what we use, internal ids included (`Square/Models`: `ShopDetails`, `BookingProfile`, `BookableService`, `TimeSlot`, `Appointment`), and each feature's `Mappers/` turns those into the DTOs (`ShopInfo`, `BookingConfirmation`). The DTOs are the API contract, designed for accuracy, stability and simplicity rather than to fit the wireframe-built UI, which adapts to them (the user's choice, 2026-10-04). They carry data, not presentation: phone in E.164, a structured address, opening hours as `{ day: 0–6, opens: "HH:mm:ss", closes }`, and times as UTC instants (`startAt`; availability is a plain list of them), with `ShopInfo.timeZone` telling the UI to show every time in the shop's timezone, not the browser's. Booleans read as `Is…`/`Can…`/`Has…`. `Common/` holds code any feature can use, in the same layer folders (`Common/Extensions/TimeZoneInfoExtensions`: `zone.ToLocalDate(instant)`, `zone.GetDayRange(date)` and `zone.GetMonthRange(date)` → `Common/Models/DateTimeRange`, DST-safe; `range.Intersect(other)` in `Common/Extensions/DateTimeRangeExtensions`; the folder isn't `Shared/` because that's a VB keyword and CA1716 fails the build). Outcomes the caller can act on (a taken time, details to correct) are exceptions deriving from `Common/Exceptions/ProblemException` (status, `code`, title); `Infrastructure/Problems/Handlers/ProblemExceptionHandler` writes them as ProblemDetails carrying `code` (e.g. 409 `slot_unavailable`), while `Square/Handlers/SquareExceptionHandler` only maps Square and Key Vault failures to 502 `square_rejected`/503 `square_unavailable`. The Square SDK's `SquareApiException` puts Square's whole response body in its message, and Square's error details can repeat a customer's name or phone, so `SquareService` runs every call through `CallSquareAsync`, which throws `Square/Exceptions/SquareRequestFailedException` instead (status plus Square's error category, code and field, never `detail`; the full response is in Square's Developer Console API Logs); `Infrastructure/Problems/Configuration/ProblemsSetup` gives every other error body a `code` (`validation_failed` for validation problems, then by status: `unauthorized`, `not_found`, `rate_limited`…, any other 4xx `bad_request`, 5xx `internal_error`) and `type` `about:blank` where ASP.NET has no RFC link, so every error has `type`, `title`, `status` and `code` (`TestSupport/ProblemAssert` checks all four). Mapper tests read the recorded responses in `Fixtures/Square` with `SquareFixture.ReadAs<T>`; `Infrastructure/<Concern>/` holds app-wide setup (`Auth/`, `Cors/`, `KeyVault/`, `Headers/`, `Problems/`, `RateLimiting/`: fixed-window limits per client IP from `RateLimits:*` on `POST /api/session`, `POST /api/bookings` (BR-13) and cancel/reschedule (their own `Manage` limit, so used-up booking attempts never block managing a booking), and the anonymous `GET /api/bookings/next` (`NextTimes`), 429 with `Retry-After`; `Telemetry/`: OpenTelemetry (in Azure it's the only log provider, so the console never writes unredacted text to the log stream), with `RedactingLogProcessor`/`RedactingSpanProcessor` added ahead of Azure Monitor's exporters so phones and emails are masked, and name/phone/email fields lose their value, before anything is exported (BR-23); `TelemetrySetupTests` books with a made-up customer through `TestSupport/TelemetryCapture` and checks none of it is exported). Configuration classes are named `*Settings` (`*Options` would clash with ASP.NET's `CorsOptions`). One project, no Domain/Infrastructure project split until a second deployable or the database needs it. Keep business rules in plain classes (no `HttpContext` or Square types) and Square behind an interface.

**Reviews (#245).** `Features/Reviews`: anonymous `GET /api/reviews` returns `{ testimonials: [{ id, quote, author, source, rating }], rating: { score, count, url } | null }`. `ReviewsService` (singleton) reads the owner's `reviews.json` from the private content container through `IMediaStorage` and keeps it in `StaleCache` until the media webhook marks it stale (or 60 minutes pass). A missing file serves no reviews; an unreadable one keeps the last good copy, or serves no reviews (logged, 200) when there is none yet. `ReviewsFileMapper` is lenient: it skips bad testimonials, defaults `rating` to 5 and `source` to "Customer review", and drops an invalid rating or a non-https link. Google's reviews API replaces the file as the source in #37 behind `ReviewsService`. Tests use `FakeReviewsHttp` and `ApiFactory(reviews:)`.

**Gallery, announcements and media webhook (#204).** The API reads the environment's storage account with its managed identity (`Infrastructure/Storage`: `IMediaStorage`, `AzureMediaStorage` over `Azure.Storage.Blobs`; `MediaStorage:AccountName`, `MediaContainerName` and `ContentContainerName` in `appsettings.{Environment}.json`, short names with the URIs built in code). Anonymous `GET /api/gallery` (`Features/Gallery`) lists the media container's `gallery/` folder (BR-34: jpg/jpeg/png/webp/avif, newest upload first by the blob's creation time, alt text from the file name) as `[{ src, alt, uploadedAt }]`. Anonymous `GET /api/announcements` (`Features/Announcements`) reads `announcements.json` from the private content container, skips invalid items (BR-33; a button link must be a site path, https, tel: or mailto:, with no control characters) and cleans each `bodyHtml` with HtmlSanitizer (`AnnouncementBodySanitizer`), and returns only the ones showing today on the shop's calendar from Square's timezone (BR-30), so a scheduled post never reaches the browser. Both keep their data in `StaleCache` (60 minutes; the last copy is served with a warning when storage fails) and answer 200 with none when storage can't be read and no copy exists, which is cached for a minute so an outage doesn't make every request wait out the timeout. `POST /api/webhooks/media` (`Features/Media`) takes Event Grid's batches: it answers the subscription handshake by echoing `validationCode` (without the key), and `BlobCreated`/`BlobDeleted` in `gallery/` or on `announcements.json` mark that cache stale. Every other call needs the `x-media-webhook-key` header, compared in fixed time with `MediaWebhook:Key` (Key Vault secret `MediaWebhook--Key`); with no key set every call is 401. Tests use `FakeMediaStorage` and `ApiFactory(media:)`.

**Find my bookings (#214, BR-20).** `POST /api/bookings/lookup/code` `{ phone }` (texts the one-time code) always answers 202 with no body, whether or not the phone has bookings (it never asks Square), and `POST /api/bookings/lookup/verified-list` `{ phone, code }` (checks the code) answers `[{ id, startAt, manageToken }]` (upcoming, not cancelled, soonest first, every Square customer with the phone, read up to the booking window's end; nothing is stored) or 400 `code_invalid`. Both live in `BookingEndpoints`/`BookingService` behind the session token. `Twilio/` mirrors `Square/`: `ITwilioVerifyService` (`StartAsync`, `CheckAsync`) over the official `Twilio` package with an API key; a 404 or 429 from the check is a wrong code, any other failure becomes `TwilioRequestFailedException` (status and Twilio error code only) and the handler answers 503 `verification_unavailable`. `TwilioSettings` (`VerifyServiceSid` in `appsettings.Development.json` only so far; secrets `Twilio--AccountSid`, `Twilio--ApiKeySid` and `Twilio--ApiKeySecret` in Key Vault, set with `Set-TtbSecrets.ps1`) is validated at startup only once any value is set, so environments without Twilio still start and answer 503. Limits: per IP `RateLimits:LookupCode` and `LookupVerifiedList`, plus `RateLimits:LookupCodePhone` per phone on code requests (`PhoneRateLimiter` keys by a SHA-256 of the phone, in memory; a refusal is `RateLimitedException`, 429 `rate_limited` with `Retry-After`). The cloud dev API will not start until `Twilio--AccountSid`, `Twilio--ApiKeySid` and `Twilio--ApiKeySecret` are all in its Key Vault (run `Set-TtbSecrets.ps1` before deploying), because its `appsettings.Development.json` sets the SIDs and the validator then requires the rest. A check counts as a wrong code only for Twilio error 20404 (verification expired, approved or deleted) or 60202 (max check attempts); Twilio gives a wrong Verify service SID the same 20404, so a mistyped SID looks like wrong codes, not a 503. A cancelled caller stops before Twilio is called and is not a failure; an HttpClient timeout is. The verified list also has a per-phone limit (`RateLimits:LookupVerifiedListPhone`). Tests fake Twilio with `FakeTwilioVerifyService` (`ApiFactory(twilio:)`) and, over HTTP, `FakeTwilioHttp`.
