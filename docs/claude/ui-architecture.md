# UI architecture details

Moved from CLAUDE.md; read it when working on the home sections, the booking and manage pages, the shop slice, announcements or the backdrop.

**Features own their state.** `app.routes.ts` loads `features/home` eagerly (it's the prerendered landing page, so a click shouldn't wait on a second download) and lazy-loads `features/booking`; each `<feature>.routes.ts` registers its effects with `provideEffects`. The root `layout` slice (mobile menu, `src/app/store/`), `shop` (`features/shop/state/`), `announcements` (`features/announcements/state/`) are registered at bootstrap, as root reducers in `app.config.ts`: the header and footer read shop and announcements on every page, and shop saves only part of its slice, which needs the slice's initial state in place before the saved copy merges over it (a lazy `provideState` slice would lose its unsaved fields); `booking`, `home`, `gallery` and `reviews` are lazy `provideState` slices on the routes that show them (`home`, `gallery` and `reviews` on the home route, so no other page requests them; `home` keeps only the open times and the parked SMS signup, none of it saved), and nothing that renders on another page may read them. Every derived selector lives on its feature's `extraSelectors`, wrapped one argument per line, with any logic in a named `to…` function and projector parameters named after the field they get. Slices are independent: `AppState` types only `layout`, and nothing reads another slice through it.

**Mocked backend.** `SmsSignupService` returns local data and notes the endpoint it should eventually call. The reviews and listing rating are not mocked: `ReviewsService` (`features/reviews/`) calls `GET /api/reviews` (#245), anonymous and browser only. Booking is real (#41): `AvailabilityService` gets `GET /api/bookings/availability?from=&to=` (shop-calendar days, both included, at most 31; only the open days, with all their times, so a picked day needs no second request; #205) and `BookingService` posts `POST /api/bookings`; the booking page is one form in a PrimeNG `p-stepper` (the client asked for steps), vertical on phones and laid out horizontally from `lg` by CSS grid in `booking.scss` (one template; panels are hidden, not animated, there): Day → Time → Details & confirm (`models/booking-step.model.ts`; just Confirm when moving), each header showing its pick and disabled until the step before is done (not `linear`, which would also stop going back); picking a day clears the old time and opens Time, picking a time opens the last step, and focus follows the opened step's header; the last step holds name and phone and a confirm button that names the picked time; a booking made is saved and opens its manage page, `pages/manage-booking` (`/book/manage/{id}`, with `isJustBooked` in the router's navigation state, `models/manage-page-state.model.ts`), which loads it like any manage link and, right after booking, shows the link to keep, Copy link and an `.ics` "Add to calendar" (`utils/ics.utils.ts`); opened later, it loads the booking and offers Add to calendar first; either way it offers Reschedule (it opens the booking page itself at `/book/manage/{id}/reschedule`, which reads the booking id from the route's path, not an input, so `/book?id=…` stays a plain booking, with the token and current time in the navigation state (`models/reschedule-page-state.model.ts`): the same page without name and phone, showing the current time and a "Back to your appointment" link, the same leave guard ("Leave without moving?"), "Move to …" sending `POST …/reschedule`, a taken time handled as when booking, then back to the booking's page with an "Appointment moved" toast; a booking that started or was cancelled meanwhile shows a notice) and Cancel (a `p-confirmdialog`, Keep appointment by default, then `POST …/cancel`) until it starts (BR-07; a 409 `booking_started`/`booking_cancelled` reloads it), each confirmed by a success toast, a failed cancel showing an inline error with Retry (a cancel finishes even if the customer leaves the page; the leave guard holds them on the booking page while a booking or move is sent, so its outcome shows there); the booking effects sit on a parent route over `/book`, both manage pages and the reschedule route, and the booking page's first month opens with `BookingPageOpen` (`openFirstMonth`, once the shop's clock is known), and every month change or reload dispatches `AvailabilityRequest({ dayRange })` (`loadAvailability`); the Day step is an inline `p-datepicker` (`components/date-step`, the client asked for a calendar): only open days enabled, filling-up days marked with a dot (BR-15), Back and Next disabled through `pt` at the booking window's edges, and a legend below on phones and beside it from `lg`, styled by `theme/tokens/components/datepicker.ts`; a manage link from elsewhere carries the token in its `#t=` fragment, which the page moves from the address bar into the navigation state (the router restores it on a reload), or right after booking the booking page hands it over the same way; it's sent only as `X-Manage-Token`; the booking page's "Already booked?" link goes to `/book/manage` (#214, `pages/find-bookings`, in `CLIENT_ROUTES`): phone (`components/phone-field`, shared with the details step, sent as E.164) → texted code (digits only, 4 to 10, `utils/lookup-code.utils.ts`; a wrong one, `code_invalid`, shows an inline notice and can be retried, with "send a new code" and "use another number") → the upcoming bookings (`FoundBooking`, soonest first, on the shop's clock), each a `routerLink` to its manage page with the token in the `#t=` fragment (`toManageCommands`/`toManageFragment`); an empty list is an info notice, not an error. The page keeps all of it in its own signals and calls `BookingService.sendLookupCode`/`getVerifiedList` directly (the booking slice holds only availability, its submit state and the `lookupToken`): the step (`models/lookup-step.model.ts`), a request-in-flight flag that locks the form and blocks a second send, the notice (`toProblemNotice` over `LOOKUP_PROBLEM_NOTICES`, a "code sent" success notice after each send) and the found bookings; focus goes back to the active field when a request ends; a request still sent when the page closes is dropped with it, and a right code saves the API's `lookupToken` (`LookupTokenSave`) in the slice and the tab's `sessionStorage` (`sessionStorageSyncReducer`), and opening the page with one asks `refreshVerifiedList` for the list again (the list itself is never kept), a 403 `lookup_expired` clearing it and returning to the phone step; leaving the tab forgets it (BR-22); the manage page uses the `page` layout utility (`theme/tailwind/theme.css`, sized by the `--p-brand-page-width`/`--p-brand-page-gutter` tokens the footer shares) like `/book`; `guards/leave-booking.guard.ts` asks "Leave without booking?" or "Leave without moving?" in the page's `p-confirmdialog` while the page's `hasUnconfirmedPick` holds, and refuses to leave while `isSubmitting` (`models/leave-confirmable.model.ts`; `ConfirmationService` is provided on the booking routes so the guard and the dialog share it), and the page adds a `beforeunload` listener only while a day is picked and not yet booked or moved. It maps the API's ProblemDetails `code` (`shared/models/problem-code.model.ts`) to a `Notice` (`shared/models/notice.model.ts`, all of them constants in `config/booking-notices.ts`, with tables of which error code shows which, picked by `shared/utils/problem.utils` `toProblemNotice`: severity, text, retry; every problem notice ends with call, text and Square's booking site, BR-14), which `shared/components/notice-message` (`NoticeMessage`, the app's only message component; a notice can carry a `link` to another page) shows inline at the top of the page (a failed bot check too), and a 409 `slot_unavailable` takes that time off the open days; the load effect maps its own failure the same way. The slice holds the month in view (`dayRange`, `models/day-range.model.ts`: `firstDay`/`lastDay`, built by `toMonthRange` and sent to the API as they are; a calendar month always fits its 31-day limit), its open days and their `loadStatus` (a spinner overlays the calendar while it's pending; the availability notice is derived from it); the page keeps the booking form (`models/booking-form.model.ts`: name, phone, date as a shop-calendar ISO day, `startAt`; each child gets the controls it edits as inputs and binds `[formControl]`; a day's times come from the slice's days), so name and phone never enter the store's state; `confirm()` dispatches `BookingRequest` (with the page's idempotency key, kept while the same booking is retried and dropped on any edit) or, when moving, `RescheduleRequest`, and the slice's effects send it (`requestBooking`, `requestReschedule`), open the booking's page (`openBookedPage`, `returnToMovedBooking`), and turn a failure into `submitNotice`, shown above the steps (a booking that started or was cancelled before it moved is one too); a taken time rides on the failure as `takenStartAt`, which the reducer takes off the open days, and the page clears any picked day or time that's no longer open and reopens its step; `submitStatus` locks the form while it's sent and, once `Success`, stops a second send and the leave question; `BookingPageOpen` starts it over each time the page opens. API request and response types are in `dtos/` (`available-day.dto.ts`, …), apart from `models/`. The booking window comes from `shopFeature.selectBookingSettings`, and every booking date and time shows on the shop's clock. The mocked e2e fixture serves made-up availability (`e2e/support/booking.ts`); `environments/` has one file per build configuration (`development` local, `devCloud`, `test`, `production`), typed by `environment.model.ts`; build request URLs as `${environment.apiBaseUrl}/path`.

**Shop data** (name, phone, address, hours, socials, booking settings) comes from Square through `GET /api/shop`, which needs no session token (#39): the root `shop` slice (`features/shop/state/`) loads it in the browser on the first navigation and retries on the next one after a failure, and its `shopFeature` selectors derive the phone links, location and map URLs, hours in minutes and social links. `core/config/shop-info.ts` keeps `SHOP_FALLBACK` (the `ShopInfo` name, E.164 phone and Square booking URL, same field names as the API, shown until the shop loads and on Express's error page; it is edited by hand, so when the name, phone or booking page changes in Square, change it too, because nothing compares it with Square: dev and test read the sandbox, and a build-time fetch would mean opening the API to the CI runners), `SHOP_CONTENT` (site content Square doesn't hold: just reviews until #37; it moves into the home slices once they own it) and `HOME_SECTIONS`. There's no venue line or area text ("Route 1 in Fredericksburg"): Square doesn't hold them, and the site shouldn't need upkeep; a later issue may source the venue from Square. `features/shop/services/shop-hours.service.ts` builds the hours table (shown by `features/shop/components/hours-list`) and the live "Open now" status from the slice, on the shop's clock (`timeZone`), not the browser's. Shop models are one type per file in `features/shop/models/`; the generic ones the shared utils use (`weekday`, `week-time`, `phone-links`, `nav-item`) are in `shared/models/`, and `SHOP_FALLBACK`'s in `core/models/`. A feature without a page (shop) still lives in `features/<name>/` with its own `state/`, `services/`, `models/` and `components/`; `store/` keeps only the `layout` slice, `AppState` and the meta reducers. Tests use the made-up `src/testing/test-shop.ts`, which the mocked e2e suite also serves for `/api/shop`.

**Search and share metadata (#70).** Every route sets `data.seo` (`RouteSeo`: `title`, `description`, `isIndexed`; `{shopName}` and `{city}` are filled in). `SeoTitleStrategy` (the router's `TitleStrategy`) applies the deepest active route's `data.seo` through `SeoService`, which writes the title, description, canonical link (only for indexed routes), `robots`, Open Graph and Twitter tags in the browser and while prerendering; `app.routes.seo.spec.ts` fails for a route without `data.seo` and checks the 60-character title and 120-160-character description limits. The shop name comes from the `shop` slice (its `SHOP_FALLBACK` name at prerender); the city is `SHOP_FALLBACK.city`, edited by hand like the rest of the fallback, because the prerender has no API data. One image pair serves every route: `public/social/og-v1.jpg` (1200x630) and `twitter-v1.jpg` (1200x600), made by `npm run social:images` (`scripts/generate-social-images.ts`, `sharp`) from `public/assets/logo.png` and committed; change the `-v1` in `seo.service.ts` and the script together when the artwork changes, and Express caches `social/` for a year. A new page also needs its path in `serverRoutes` (`app.routes.server.ts`), or Express answers 404 for it.

**Backdrop.** `shared/components/backdrop` renders the fixed background. It is the wireframe's scroll-scrubbed video, on the home page only: `FrameScrubber` (`frame-scrubber.ts`) progressively loads 6 clips × 61 AVIF frames from `public/assets/backdrop/<desktop|phone>/frames/c1..c6` onto a canvas, with 7 keyframes (`keys/k1..k7`) anchored to page sections; the last keyframe holds through the footer. It is scroll-triggered, not scrubbed: when a section's title crosses one fixed line (`KEYFRAME_TRIGGER_LINE`, 70% down the screen, so the title is 30% in view; the section's top for one without a title) `Backdrop` sets that section's keyframe as the target, and the scrubber plays the clips to it at a steady pace with an ease in and out, then holds the still. `Backdrop` picks the set once with `matchMedia('(min-width: 48rem)')`: phones get the portrait crop. The files come from `tools/backdrop-frames`. (The README's "not in this version yet" note about the backdrop predates the scrubber.)
